# 06 技能、扩展与集成

## 1. 技能（Skills）

### 机制

- 一个技能就是一个目录，里面有一个 `SKILL.md`（frontmatter 里写 `name` 和 `description`），可以附带 `scripts/`、`playbooks/` 等子目录。**和 Claude Code 的技能格式一样**，所以 `~/.claude/skills` 里的技能可以直接用（Alma 的日志里有 `Found 7 Claude Code skills`）。
- 数据库只存开关和排序（`skills` 表：id、path、enabled、sort_order），技能内容一律从文件系统读取。
- 注入方式：把所有已启用技能的 `name` 和 `description` 放进系统提示词，模型判断需要时再去读完整的 `SKILL.md`（渐进加载，省 token）。
- 技能执行操作靠调用 `alma` CLI（比如 `alma config set`、`alma plan submit`、`alma herdr send`），CLI 再去调本地的 HTTP API。

## 2. MCP

- **两张表**：`mcp_servers` 存 config（JSON，包含 transport 类型、命令或 URL、环境变量），`mcp_oauth_tokens` 存 OAuth 2.1 的完整状态（动态客户端注册、PKCE 的 code_verifier、refresh token、过期时间）。
- **连接管理**：`/api/mcp-client/status` 看连接状态，`/reconnect/:name` 重连，`/refresh` 重新拉工具列表。
- **资源**：支持 resources、resource templates、订阅资源变化。
- **随包带了 uv/uvx 和 bun**：Python 写的 MCP 用 `uvx` 跑，JS 写的用 `bun` 或 `npx` 跑，用户不用自己装运行时。
- **透传给 ACP agent**：见 05 的 3.5 节。

**cjh 建议**：直接用官方的 `@modelcontextprotocol/sdk` client。MVP 支持 stdio 和 Streamable HTTP 两种就够了，OAuth 放到 P1。

## 3. 插件

- 插件的来源分 local、global、npm、url、marketplace
- 安装时声明需要的权限，用户逐项授权（`plugin_permissions`，状态分 granted、denied、pending）
- 插件有自己的键值存储（`plugin_state`）和设置项
- 插件可以带主题（`/api/plugin-themes`），可以做登录（`/api/plugin-sign-in`）
- 有更新检查（事件 `plugin_updates_available`）

cjh 放到 P2。技能加 MCP 已经能覆盖大部分扩展需求了。

## 4. Hooks

`/api/hooks` 可以读写一份 hooks 配置文件，支持热重载，还有一个应用退出前触发的钩子（`app-will-quit`）。具体用法和 Claude Code 的 hooks 类似。P2。

## 5. 定时任务和 Heartbeat

- **cron job**：每个任务有 cron 表达式、目标线程、提示词，可以启停、立即执行、查看执行历史。执行时就是往目标线程发一条 `generate_response`（`source` 标记为 cron），停止的时候会核对是不是这个 cron 发起的那一轮。
- **heartbeat**：按固定间隔“醒来”一次，读取 `HEARTBEAT.md` 里写的检查项，决定要不要主动做事或提醒用户。

**cjh 的第一个实际用途**：你每天 7:30 的 sub2api 状态汇报，可以做成一个 cron 任务：

```
cron: 30 7 * * *（Asia/Shanghai）
thread: “sub2api 日报”
prompt: 通过 ssh 查询 HK 上的 sub2api 健康状态和过去 24 小时的用量，汇总后发到飞书
```

## 6. 聊天渠道桥接

### 通用结构

```
外部平台（飞书、微信、Telegram）
   │ 收到消息
   ▼
Bridge（一个 WebSocket 客户端）
   1. 查 channel_mappings：(platform, external_chat_id, external_user_id) → thread_id
      找不到就新建一个线程并写入映射
   2. 群聊的上下文通过 ephemeralContext 带过去（只在这一轮生效，不落库）
   3. 图片落到本地临时文件，转成 file parts
   4. WS 发送 generate_response，source 标为对应平台
   5. 监听 message_delta 和 tool_use：显示“正在输入”，在平台允许的范围内流式更新回复
   6. generation_completed 时把最终回复发出去；出错时给用户一条简短的报错
```

### Alma 在这块做了几个很实用的处理

- **承诺检测**：模型说了“我这就去做”却没调用工具时，用工具模型判断一下，确认是这种情况就自动追发一条系统消息，让它立即执行。
- **自动修复**：
  - 遇到 “stale itemId” 错误（OpenAI Responses API 的历史 item 失效），把消息里的 itemId 清掉后自动重试
  - 遇到 “string too long”，自动开一个新线程，把渠道映射改到新线程上，再重发
- **短时间去重**：同一个线程刚发过回复的，30 秒内不重复推送。
- 平台相关的命令：`/start`、`/new`（新线程）、`/stop`、`/model`（换模型）、`/help`。

### 各平台

| 平台 | 接入方式 |
|---|---|
| 飞书 / Lark | 用随包带的 `lark-cli.exe` 走扫码授权（`connect/start` → 轮询 `connect/state`），日志在 `%TEMP%\alma-logs\feishu-*.log` |
| 微信 | 扫码登录（`/api/weixin/qrcode`），登录状态存在 `weixin-state/` |
| Telegram | Bot Token，支持群组、话题、表情回应、置顶 |
| Discord | discord.js |

**cjh 建议**：飞书优先用官方开放平台的机器人（长连接事件订阅），不要依赖第三方 CLI。微信目前没有官方的个人号接口，风险自担，放到最后做。

## 7. 记忆

- **存储**：`memories` 表存内容，sqlite-vec 的 `memory_embeddings` 存向量，embedding 模型在本地跑（`embedding-models/` 目录）
- **写入**：从对话里提取事实（可以是工具模型在后台做，也可以由模型主动调用）
- **检索**：每一轮生成前按语义检索出相关记忆注入上下文（事件 `memory_retrieval_progress`）
- **整理**（“睡眠”）：在空闲时、条数到阈值时、定时或手动触发。依次做精确去重、过期清理、孤儿清理、相似合并、LLM 筛选，被淘汰的移到 `memory_archive`，并且可以恢复

**cjh 建议**：P1 先做最简单的版本。记忆存成 Markdown 文件（一条一个文件，或者一个 `MEMORY.md` 索引），用 FTS5 关键词检索。效果不够再上向量检索。
