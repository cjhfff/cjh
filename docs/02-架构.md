# 02 架构

## 1. Alma 的进程结构（Windows 版实测）

```
Alma.exe                         原生桌面壳（窗口、托盘、WebView 渲染前端）
 ├─ go\alma-server.exe           Go 服务：原生能力（电源管理、画中画、截屏、终端工作区 herdr、插件、活动状态）
 │                               监听 127.0.0.1:23001，路由前缀 /__alma_go（78 条）
 ├─ runtime\alma-server.exe      其实是改了名的 Node 运行时，执行 lib\server.mjs serve
 │                               主业务服务：监听 127.0.0.1 上的随机端口，提供 /api/*（约 700 条）和 WebSocket
 │   ├─ ACP agent 子进程          claude-agent-acp、codex-acp 等，通过 stdio 通信
 │   ├─ MCP server 子进程         stdio 类型的 MCP
 │   ├─ node-pty 终端
 │   └─ bun.exe                  执行模型写的脚本（programmatic tools）
 └─ lark-cli.exe ×2              飞书桥接
```

几点观察：

- **历史上从 Electron 迁出来过**：数据目录里有 `electron-imported` 标记文件，服务端代码里也还有 electron 相关的引用。现在的壳是原生实现，更新包叫 `alma-native`。
- **核心生成链路正在往 Go 迁移**：代码里有一个 “Go turn bridge”，环境变量 `ALMA_GO_TURNS=1` 打开后，流式生成改由 Go 进程负责。说明 Node 单进程在高负载时有性能瓶颈。cjh 第一版不用考虑这个。
- **Node 服务用的是改名的运行时**：这样任务管理器里显示的是 alma-server，而且不依赖用户机器上装没装 Node。

## 2. 技术栈（从打包文件里识别出来的）

| 层 | Alma 用的 |
|---|---|
| 前端 | React、Tailwind、Radix UI、i18next |
| 前端里的重型组件 | shiki（代码高亮）、Monaco（编辑器）、xterm（终端）、Mermaid（图表）、pdf.js（PDF 预览） |
| HTTP | Express 和 Hono 同时在用 |
| 实时通信 | WebSocket（`ws`） |
| 数据库 | better-sqlite3 + drizzle-orm；FTS5 全文检索；sqlite-vec 向量检索 |
| 模型调用 | Vercel AI SDK，带 `@ai-sdk/openai`、`openai-compatible`、`google`、`google-vertex`、`gateway` |
| ACP | ACP agent 被包装成 AI SDK 的 LanguageModelV3 provider |
| 终端 | node-pty |
| 渠道 | discord.js，Telegram（自己写的 Bot API 客户端），飞书（lark-cli），微信 |
| 邮件 | imapflow + nodemailer |
| 随包带的工具 | bun.exe、uv/uvx（跑 Python 写的 MCP）、rtk.exe、lark-cli.exe、Chrome 扩展、TTS（Python + sherpa） |

前端页面路由只有这几个：`/`、`/chat`、`/settings`、`/quick-chat`、`/permission-overlay`、`/more-menu`、`/team`、`/agents`、`/agents/:host/:pane`、`/simulator/:host/:udid`。可见大部分功能都是聊天主界面里的侧边栏和弹层，不是独立页面。

## 3. 数据目录

| 位置 | 放什么 |
|---|---|
| `%APPDATA%\alma\chat_threads.db` | 唯一的主数据库，SQLite WAL 模式。线程、消息、provider、设置全在里面 |
| `%APPDATA%\alma\logs\native.log` | 主日志，Node 和 Go 两边的输出都写进来，按 `[ACP]`、`[MessageBridge]` 这样的 tag 区分 |
| `%APPDATA%\alma\workspaces\`、`embedding-models\`、`whisper_models\`、`gallery_cache\`、`weixin-state\` | 各模块自己的文件 |
| `%APPDATA%\alma-native\ui-prefs.json` | 原生壳的界面偏好 |
| `~\.alma\npm-cache\` | 用 npx 拉 ACP agent 时的独立 npm 缓存 |
| `%TEMP%\alma-logs\` | 飞书、微信桥接的日志，按天切分 |

**cjh 可以照这个思路**：一个 SQLite 主库，一个主日志（按 tag 区分模块），大文件按模块分目录存放。

## 4. 一次对话的完整链路

这是整个产品最核心的一条路径：

```
前端输入框
  │  WS 发送 {type:"generate_response", data:{threadId, userMessage:{role:"user", parts:[...]}, model?, tools?, reasoningEffort?, ...}}
  ▼
服务端 WS 处理
  1. 线程正在生成吗？
       是 → steer：把这句话并入正在进行的这一轮，结束
  2. 确定用哪个模型：data.model → 线程上的 model → 设置里的 chat.defaultModel
       模型字符串格式是 "providerId:modelId"；没带前缀就自动补上
  3. 调用 generateChatResponse(threadId, model, userMessage, options)
       a. 把用户消息写入 chat_messages，挂到当前活跃分支上
       b. 沿当前分支组装历史，必要时先压缩
       c. 准备工具：内置工具 + 已启用 MCP 的工具 + 技能说明 + 线程的 enabledMCPServerIds
       d. 用 AI SDK 的 streamText 调用模型（ACP agent 也走这条路，见 05）
       e. 流式事件：message_start → message_delta / tool_use / tool_output_streaming … → message_stop
  4. 流结束后：写入 assistant 消息，写 usage_records 和 agent_op_traces，
     需要的话再让工具模型生成标题
  ▼
广播（thread sync）
  所有连着的客户端都会收到 message_added、message_updated、thread_generating 等事件：
  GUI 窗口、快速对话窗口、手机中继……
  ▼
渠道桥接（飞书、Telegram、微信）
  它们本身也是 WebSocket 客户端：收到外部消息后发 generate_response，
  再监听 message_delta 和 generation_completed，把回复转发回外部平台
```

**这里最值得学的设计**：

1. **所有入口共用一条生成管线**。GUI、快速对话、定时任务、聊天渠道，都是“往 WS 发一条 generate_response”。新加一个入口只需要写一个 WS 客户端，生成逻辑一行都不用改。
2. **消息格式直接用 AI SDK 的 UIMessage**（`role` + `parts[]`），整条 JSON 存进库里。存储、传输、渲染用同一种格式，不用来回转换。
3. **消息是一棵树**：靠 `parent_id` 和 `slot_id` 组织，线程上记录当前活跃的是哪条分支。重新生成、编辑重发、切换版本都只是换一条分支。
4. **生成状态由服务端统一持有**（activeGenerations），客户端断线重连后还能接上；同一线程同时有两个请求时，用 supersede 和 fork 来裁决。

## 5. 扩展能力怎么调回主程序

技能文件里写的是“运行 `alma config list`”“运行 `alma plan submit`”这类命令。也就是说，随包带了一个 `alma` CLI（`resources\cli\alma`），它内部调本地的 HTTP API。

好处是：**任何 agent，包括外部的 Claude Code，只要能执行 shell 命令，就能操作主程序**，不需要为每种 agent 单独做工具协议。cjh 建议也带一个 `cjh` CLI。
