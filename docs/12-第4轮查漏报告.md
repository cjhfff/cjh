## 二、安全专项核查结论

1. **已有安全逻辑回归检查**：
   - **线程级 ACP 会话隔离**：`src/server/acp/manager.ts` 仍按 `threadId` 独立维护 `this.sessions`，线程删除、归档、切换工作目录、切换 Provider 及空闲超时均会调用 `releaseThreadSession` 销毁子进程。

   - **ACP 权限模式 Fail-Closed 与 `PermissionGate` 抽离核查**：
     - `src/server/acp/manager.ts:741-751` 保留了「无活跃线程绑定时立即拒绝（返回 `rejectOptionId` 或 `cancelled`）」的 Fail-Closed 逻辑；
     - `src/server/permissions/gate.ts:48-85` 保留了 `rejectOption` 识别与超时自动拒绝定时器；
     - **但抽离后引入了 2 个新问题**：一是 `builtin.ts` 与 `gate.ts` 对未知或非 `'reject'` 的拒绝 `optionId` 存在 **Fail-Open 放行漏洞**（**P0-1**）；二是超时/拒绝广播的 `outcome` 未统一归一化为 `'rejected'`，导致飞书侧将 ACP 超时/拒绝误判为「已允许」（**P0-4**）；三是 ACP 子进程异常退出时未清理 `PermissionGate` 中挂起的请求（**P2-2**）。
2. **新工具与密钥存储安全检查**：
   - **`fs_*` 路径越界**：发现**悬空符号链接写越界**与 **`fs_grep`/`fs_list`/`fs_glob` 符号链接读越界**（**P0-2**）。
   - **`shell_exec`**：通过 `runWithPermission('shell_exec', true, ...)` 走权限确认，超时（默认 120s）与 `taskkill /T /F` 进程树清理、30KB 截断均已实现。
   - **`web_fetch`**：`src/server/tools/web.ts:131-133` 严格限制 `parsed.protocol === 'http:' || parsed.protocol === 'https:'`。
   - **飞书 App Secret 与搜索 API Key 加密存储**：通过 `app_secrets` 表配合 `SecretVault`（AES-256-GCM）加密存储；`GET /api/settings`、`PUT /api/settings` 与 `GET /api/data/export` 均只返回 `has*` 布尔值与 `SecretVault.mask(...)` 掩码预览，不回明文。

#### [P0-1] 内置工具权限门禁 `runWithPermission` 与 `PermissionGate.resolvePermission` 存在 Fail-Open 漏洞：传入非 `'reject'` 的拒绝或未知 `optionId` 时会直接放行执行高危工具
- **位置**：
  - [builtin.ts](file:///D:/workspace/cjh/src/server/tools/builtin.ts#L91-L102)
  - [gate.ts](file:///D:/workspace/cjh/src/server/permissions/gate.ts#L108-L135)
- **问题**：
  1. `PermissionGate.resolvePermission(requestId, selectedOptionId)`（`gate.ts:108-135`）仅对 `'__cancel__'` 和 `'__reject__'` 做了拒绝分支处理，未校验 `selectedOptionId` 是否属于 `entry.dto.options` 中的合法选项，也未将命中 `entry.rejectOptionId` 的选项归一化为拒绝。
  2. `buildBuiltinToolSet` 中的 `runWithPermission`（`builtin.ts:91`）采用了黑名单判断而非白名单：
     ```ts
     if (outcome.outcome !== 'selected' || outcome.optionId === 'reject') {
       throw new Error(`权限被拒绝：用户拒绝执行 ${toolName} 或审批已超时`)
     }
     ```
- **复现或依据**：
  当 `fs_write` / `fs_edit` / `shell_exec` / `cron_create` / `cron_delete` 挂起等待权限确认时，若客户端通过 `POST /api/permissions/:requestId/respond` 或 WS `permission_response` 传入任何非 `'reject'` / `'__reject__'` / `'__cancel__'` 的 `optionId`（例如 ACP 风格的 `'reject_once'`、`'deny'` 或任意非法字符串 `'unknown'`），`resolvePermission` 返回 `{ outcome: 'selected', optionId: 'reject_once' }`，`builtin.ts:91` 判断 `outcome.optionId === 'reject'` 为 `false`，直接落入第 102 行 `return await fn()` **执行受保护的高危工具**，违背 Fail-Closed 要求。

#### [P0-2] 工作区越界检查 `resolveSafeWorkspacePath` 漏检悬空符号链接（Dangling Symlink），且 `fs_grep` / `fs_list` / `fs_glob` 遍历子项时未校验符号链接真实路径，可读写工作区外文件
- **位置**：
  - [workspace-fs.ts](file:///D:/workspace/cjh/src/server/tools/workspace-fs.ts#L47-L63)（`resolveSafeWorkspacePath`）
  - [workspace-fs.ts](file:///D:/workspace/cjh/src/server/tools/workspace-fs.ts#L118-L143)（`workspaceFsList`）
  - [workspace-fs.ts](file:///D:/workspace/cjh/src/server/tools/workspace-fs.ts#L281-L294)（`workspaceFsGlob`）
  - [workspace-fs.ts](file:///D:/workspace/cjh/src/server/tools/workspace-fs.ts#L336-L375)（`workspaceFsGrep`）
- **问题**：
  1. **悬空符号链接写越界**：`resolveSafeWorkspacePath`（第 50 行）使用 `while (!existsSync(probe))` 向上寻找最近存在的祖先目录。Node.js 的 `fs.existsSync` 基于 `stat`（跟随符号链接），当 `candidate` 是工作区内的**悬空符号链接**（例如 `workspace/out.txt -> D:\outside\pwned.txt`，而 `D:\outside\pwned.txt` 尚不存在）时，`existsSync(candidate)` 返回 `false`，循环直接回退到父目录 `workspace`，`realpathSync(workspace)` 校验通过并返回 `candidate`。随后 `workspaceFsWrite`（第 392 行）执行 `writeFileSync(targetFile, ...)` 会跟随该悬空符号链接，直接在工作目录之外创建并写入 `D:\outside\pwned.txt`。
  2. **`fs_grep` / `fs_list` / `fs_glob` 遍历时未校验符号链接与目录 Junction**：`workspaceFsGrep`（第 325-376 行）仅校验了根目录 `root`，在 `walk` 遍历中对每个子项直接调用 `statSync(full)` 与 `readFileSync(full)`（第 350-352 行），未调用 `resolveSafeWorkspacePath(root, full)`。当工作区内存在指向工作区外敏感文件的符号链接时，`Dirent.isDirectory()` 为 `false`，`fs_grep` 会直接跟随符号链接读取外部文件内容并在 `matches` 中返回；当工作区内存在指向外部目录的 Windows NTFS Junction（`Dirent.isDirectory()` 在 Windows 下为 `true`）时，`fs_list`、`fs_glob`、`fs_grep` 均会递归进入工作区外的目录。
- **复现或依据**：
  - 在 `workspace` 内创建指向外部不存在文件路径 `../outside_created.txt` 的符号链接 `dangling.txt`，调用 `workspaceFsWrite(workspace, { path: 'dangling.txt', content: 'escape' })`，校验不报错且外部文件被成功创建。
  - 在 `workspace` 内创建指向外部 `../secret.txt` 的符号链接 `leak.txt`，调用 `workspaceFsGrep(workspace, { query: 'TOP_SECRET' })`，`matches` 直接返回外部 `secret.txt` 的内容。
- **修复要求**：
  1. 在 `resolveSafeWorkspacePath` 回溯路径时使用 `lstatSync(probe, { throwIfNoEntry: false })`：若发现 `probe` 本身或任一中间目录是符号链接（`isSymbolicLink()`），必须解析其链接目标并校验真实目标路径位于 `realRoot` 内，若目标不存在但其解析后的父目录越界（或无法安全解析）则一律返回 `null`。
  2. 在 `workspaceFsList`、`workspaceFsGlob`、`workspaceFsGrep` 的 `walk` 遍历中，对每个子项 `full` 调用 `resolveSafeWorkspacePath(root, full)`（或校验 `realpathSync(full)` 在 `realRoot` 内），越界项直接跳过，禁止递归进入或读取。
