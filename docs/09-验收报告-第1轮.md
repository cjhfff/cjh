## 必须修（P0）

### 1. 不同线程共用同一个 ACP 会话，上下文互相串
- 位置：`src/server/acp/manager.ts` `getOrCreateLiveSession`，会话 key 是 `${provider.id}::${cwd}`
- 复现：同一个 provider、同一个工作目录开两个线程。在线程 A 说“记住暗号：蓝莓狮子”，再到线程 B 问暗号，B 直接回答“蓝莓狮子”
- 另外：两个线程同时生成时，`session.currentCallbacks` / `currentThreadId` 会被后来的覆盖，前一个线程的流式内容会串到后一个线程
- 要求：**一个线程一个 ACP session**（key 用 threadId；进程可以按 provider+cwd 复用、开多个 sessionId，也可以一个线程一个进程，选简单的）。把 `acpSessionId` 存进 `threads.metadata`。线程删除、线程换了 cwd 或 provider、空闲超过 30 分钟时释放。session/update 按 `params.sessionId` 分发到对应线程

### 2. 主密钥和本地 token 泄漏给所有子进程
- 位置：`src/main/index.ts` 用环境变量 `CJH_MASTER_KEY_HEX`、`CJH_LOCAL_TOKEN` 传给 server；`src/server/proc/spawner.ts` `buildCleanSubprocessEnv` 从 `process.env` 整个复制
- 复现：添加一个 stdio MCP（node 脚本把 `process.env` 写到文件），子进程里能读到 `CJH_MASTER_KEY_HEX`（解开所有 api_key 的主密钥）和 `CJH_LOCAL_TOKEN`
- 要求：server 启动读取后立即 `delete process.env.CJH_MASTER_KEY_HEX / CJH_LOCAL_TOKEN`；`buildCleanSubprocessEnv` 再加一层黑名单（`CJH_MASTER_KEY_HEX`、`CJH_LOCAL_TOKEN`、`CJH_DAEMON_AUTOSTART`、`CJH_APP_EXE`）。最好改成主进程通过 `utilityProcess` 的 `postMessage` 把主密钥发给 server，不走环境变量。子进程只应该拿到有意注入的 `CJH_API_URL` / `CJH_API_TOKEN`

### 3. 用户全局 Claude 设置为 bypassPermissions 时，cjh 的权限门禁完全不生效
- 现象：真实跑 Claude Agent 写文件、以及“要求拒绝”的用例，**一次 `session/request_permission` 都没收到**，文件直接被写了
- 原因：老大的 `~/.claude/settings.json` 里 `permissions.defaultMode = "bypassPermissions"`，适配器沿用了它。cjh 在 `session/new` 之后没有显式设置会话模式
- 要求：
  - provider 增加 `acp_permission_mode` 字段（默认 `default`），`session/new` 之后用 `session/set_mode`（或 configOptions 里 id 为 `mode` 的项，用 `session/set_config_option`）显式设置，日志里打印实际生效的模式
  - 解析 `session/new` 返回的 `modes.availableModes` / `currentModeId`，在 provider 设置页和对话头部显示当前模式；用户选 `bypassPermissions` 时界面给出红色警示
  - 收到 `current_mode_update` 时同步更新

## 应该修（P1）

### 4. zod 校验失败返回 500
- `POST /api/providers` 传 `{name: 123}` 返回 500，堆栈打到 stderr
- 要求：`app.onError` 里把 `ZodError` 转成 400，body 为 `{error, issues}`；JSON 解析失败也返回 400

### 5. ACP 工具卡片标题和状态不对
- 卡片标题一直是 `Preparing file…`：`tool_call_update` 带来的新 `title` / `rawInput` / `kind` 没有更新到卡片上
- `tool_call_update` 没带 `status` 时被当成 `completed`（`String(update.status || 'completed')`），应该保持原状态，只更新带了的字段

### 6. ACP 用量记错
- 结果：`inputTokens=0 outputTokens=0 totalTokens=27850`。`usage_update` 的 `used` 是上下文窗口占用，不是本轮消耗
- 要求：对照 `@agentclientprotocol/sdk` 的类型定义确认字段含义；上下文占用单独存（推 `context_usage_update` 给前端），本轮 token 从 `session/prompt` 的返回或适配器给的 usage 字段取，拿不到就记 0，不要把上下文大小当成消耗

### 7. 进程被强杀后 runtime.json 残留
- 强杀 server 后 `runtime.json` 还在，`cjh` CLI 会连到死端口
- 要求：CLI 读到 runtime.json 后先检查 pid 是否存活或 `/api/health` 是否可达，不可达时提示“cjh 未运行”

## 第 2 轮修复

针对第 1 轮复测发现的 ACP 权限模式设置 fail-open 风险已完成修复：

- **修改文件**：
  - `src/server/acp/manager.ts`
  - `src/server/__tests__/fixes-round1.test.ts`
- **修复内容**：
  - 在 `AcpAgentManager` 中新增 `tryApplyModeViaConfigOption` 与 `enforceSessionPermissionMode`，收紧 `session/new` 后的权限模式校验逻辑（fail-closed）：
    - 当目标权限模式（`provider.acpPermissionMode`）不是 `bypassPermissions`，且 agent 声明了 `modes` 字段或 `mode` 配置项，但显式设置（`session/set_mode` 与回退 `session/set_config_option`）均失败时：
      - 若 agent 返回的 `currentModeId` 为 `bypassPermissions` 或未知（空/缺失），立即调用 `releaseThreadSession` 释放该会话并抛出错误「`无法把 ACP 会话权限模式设为 <targetMode>，为安全起见已中止（...）`」，终止本轮而不发送 `session/prompt`（引擎侧随之落盘错误并以 `generation_error` 结束本轮）。
      - 若 `currentModeId` 已经等于目标模式，或为其它已知非 `bypassPermissions` 模式，则继续运行。
    - 当 agent 根本不支持 modes（`session/new` 既无 `modes` 字段也无 `mode` 配置项）时，记录 `WARN` 日志并保持现状继续运行。
    - 同步加固 `getOrCreateThreadSession` 的异常清理路径，确保初始化中途失败时释放已创建的会话映射与子进程。
- **新增测试与验证**：
  - 在 `src/server/__tests__/fixes-round1.test.ts` 新增 2 个用例（共 8 个用例）：覆盖 `set_mode` 与 `set_config_option` 均返回错误且 `currentModeId` 为 `bypassPermissions` 时以 `generation_error` 结束、未发送 `session/prompt` 且会话被释放；同时覆盖 `currentModeId` 未知时中止、`currentModeId` 已等于目标模式时继续、以及不支持 modes 的 agent 打 `WARN` 后继续运行。
  - 验证结果：`npm run typecheck`、`npm test`（`core.test.ts` 6/6 + `fixes-round1.test.ts` 8/8，共 14/14 通过）、`npm run build` 全部通过。
